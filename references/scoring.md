# 评分口径

## 一、为什么是扣分制

加分制要把「它有什么」逐项数出来，问题是一个 skill 的功能多少和「装了亏不亏」几乎无关——
功能多的包一旦夹带凭证读取，亏得更彻底。

所以默认满分，只有发现可指认的风险才扣。这也让报告可复核：每一分的去向都能反查到一条 finding。

## 二、权重与来源

| 维度 | 权重 | 装错的代价 | 为什么是这个量级 |
|---|---|---|---|
| 权限风险 | 35 | 不可撤销：数据被删、凭证被读走、被当成跳板 | 唯一一个「事后无法补救」的维度，必须单独压过其余四项之和之外的任何单项 |
| 可执行性 | 20 | 白装（跑不起来） | 发生频率最高，但代价可控 |
| 触发精度 | 20 | 抢活、污染上下文 | 与可执行性同量级：一个装不上的包会被删，一个乱触发的包会一直烦你 |
| 不可替代性 | 15 | 白装（有它没它一样） | 代价最低但最普遍，给 15 是为了让「只有一段 prompt」的包拿不到高分 |
| 维护成本 | 6 | 换机器跑不动 | 一次性摩擦，不致命 |
| 与已装冲突 | 4 | 上下文浪费 | 最轻。两个相似 skill 同时存在只是浪费 token，不会出错 |

原始设想是 30/20/20/20/10（可执行/触发/权限/替代/维护）。改动的理由只有一条：
**权限风险的量级被低估了。** 其余四维全是「浪费」，只有这一维是「损失」。把它的权重提到 35 之后，
一个文档写得漂亮但会读 `.ssh` 的包（74 分档）不会再跟一个文档写得一般的干净包（66 分档）混在一起。

## 三、判死项与总分的关系

判死项（`kill=true`）独立于总分：

```
有判死项          → 不装，无论总分多少
无判死项          → 看有没有单条高危项，以及风险维度是否被打穿（见第四节）
```

判死项只有五类，标准是「装完可能造成不可撤销的损害」：

1. `UNSAFE_ZIP_ENTRY` — zip 条目含 `..` 或绝对路径
2. `CRED_ACCESS` — 脚本引用 `.ssh/`、`id_rsa`、云厂商凭证目录
3. `NET_EXFIL` — 同一文件内既读本地密钥又发起网络请求，**且两处相距不超过 40 行**
4. `DESTRUCTIVE_HARD` — `rm -rf /`、`mkfs`、`dd if=`、格式化盘符
5. `OBFUSCATED_PAYLOAD` — base64 解码后直接 `exec`

第 3 条的两个限定词都是真跑出来的，不是预防性设计：

- **40 行窗口。** 最初写的是「同一文件内共现」。拿本机 32 个已装 skill 一跑，
  `totorosir-workbuddy-score` 被判死——它有 3232 行，读环境变量和开 socket 相距 30 行以上纯属必然。
  逐条回查四个联网脚本，命中的凭证模式**全部是 `os.environ`**，一处真凭证路径都没有。
  在 3000 行的本地服务里，「读配置」和「开端口」同文件出现的信息量是零，据此判死等于判死所有带配置的联网工具。
  改成「同文件 + 40 行内共现」之后，同一份数据里它降级为 `CRED_AND_NET`（中危 6 分，不判死）。
- **凭证分强弱。** `CRED_STRONG` 是真实凭证路径（`.ssh/`、`id_rsa`、`.aws/credentials`、`.kube/config` 等），
  参与判死；`CRED_SECRET` 要求「读环境变量」和「密钥类名字」同时出现才算——
  `os.environ["PORT"]` 不算，`os.environ["API_KEY"]` 才算。
  理由同上：把读环境变量当读凭证，是把配置读取误判成窃密。

硬编码凭证、`subprocess`、`pickle` 都只扣分不判死——它们有正当用法，判死会大量误杀。
但 `pickle` 的严重度是 high（14 分）而不是中危：反序列化不受信任的数据等价于执行对方的代码，
它和「引了一个网络库」不是一个量级。

**另有一道门与判死并列但不进判死清单：正文不足 80 字 → 直接「不装」。**
理由：它不造成不可逆损害（所以不是判死项），但也不能靠总分放行——正文为 0 的包在
「权限 / 可执行」上满分，扣完触发精度还剩 68 分，会和真包挤进「谨慎装」，
用户读完以为核实一下就能装。两道门解决两个不同问题：判死管「会不会害你」，空正文管「值不值得装」。

## 四、分档

分档看**严重度**，不看总分。总分只用来排序。

| 结论 | 条件 |
|---|---|
| 不装 | 有判死项；或正文不足 80 字；或总分 < 40 |
| 装不上 | SKILL.md 缺失，或缺 name / description —— 结构不成立，与分数无关 |
| 谨慎装 | 有单条 high 级 finding；或风险维度被扣掉一半以上；或有维度未评估导致覆盖 < 85% |
| 可以装 | 以上都不成立 |

为什么不是「按总分数值分档」：试过，真实的 32 个已装 skill 里有 24 个落进「谨慎装」——
包括用户天天在用的 `pdf`、`docx`。原因是总分把「正文没写何时用」和「脚本读 SSH 私钥」
压成了同一个数字。用户第一眼看到自己在用的工具被判「需核实」，就不会再信这份报告了。

「总分 < 40」这道门是从 60 降下来的。60 的结果是 59 分报「不装」、60 分报「谨慎装」——
**1 分之差决定装不装，这种结论没法向用户解释，也没法复核**。40 的含义是：风险维度已经塌到零，
同时至少还有一个 20 分的维度掉了六成以上，属于「不是核实某一条就能救回来」的包。

「风险维度被扣掉一半以上」是一条独立信号，不是判死：
它抓的是「单条都不够 high，但风险项扎堆」的包，典型是本地服务类工具（开端口、调子进程、
清临时目录，单看全是本职行为）。这条不靠总分，因为按总分算等于系统性歧视大包——
3000 行的包必然命中更多规则。

## 五、信息不足怎么算

不用「记 0」，也不用「排除归一」。

做法是：**未评估的维度不计分、也不重新归一，覆盖率单独显示。**

- 不给 `--installed` 时，「与已装冲突」标为未评估，其 4 分不计入总分。
  于是没有 `--installed` 的包最高只能到 96 分，而不是被抬到 100。
- 报告里「覆盖：96%」就是这件事的显式标记。读报告的人一眼能看出「这 4 分没算」，
  而不是以为满分是 100。

代价是跨包比较时 96 分档和 100 分档不同源。接受这个代价：**宁可让分数偏低可见，也不要让它悄悄变高。**

## 六、为什么三个样本必然有序

不是「跑出来是 92/66/35」，是构造上就被限住了。

无 `--installed` 时总分上限 = 96（冲突维度 4 分不计）。

**好样本（csv-cleaner）**
命中的规则全部落在「维护成本」维度（权重 6）：`ABS_PATH`(2) + `TODO_MARK`(2)。
其余五个维度权重合计 90，一条规则都没触发。
→ 总分 ≥ 96 − 6 = **90**（实测 92）。

**中样本（weekly-report）**
`SUBPROC`(10) 落在风险维度；`VAGUE_DESC`(8) + `BROAD_TRIGGER`(5) + `NO_WHEN_NOT`(3) 落在触发维度，
合计 16 ≤ 该维度权重 20，不会扣穿；`TESTS_STUB`(4) 落在不可替代性。
无判死项。
→ 总分 = 96 − 10 − 16 − 4 = **66**（实测 66）。

**差样本（env-sync）**
`CRED_ACCESS`(30) + `NET_EXFIL`(28) + `HARDCODED_TOKEN`(14) + `EVAL_EXEC`(8) + `NET_CALL`(8)
+ `CRED_MENTION`(6) + `NET_IMPORT`(4) 全部落在风险维度，合计 98 > 35，该维度扣穿为 0。
触发维度扣 25 > 20，同样扣穿为 0。
→ 总分 ≤ 96 − 35 − 20 = **41**，实测 35，且命中 3 条判死项。

**第四档（stock-watch）：文档满配，但联网 + `pickle.loads`**
文档维度一条都没扣，风险维度扣掉 26/35（`NET_EXFIL` 未命中，因为是读公开行情不是发本地数据）。
没有判死项，但有 high 级 `PICKLE`，且风险扣分过半 → 谨慎装。
这一档存在的意义：证明**文档写得好抵不掉风险分**。

三段界：好 ≥ 90，中 = 66，差 ≤ 41（实测 35），第四档 70 且必判「谨慎装」。
**92 > 70 > 66 > 35**，这个序由维度权重封顶决定，不依赖正则跑出来的具体数值。
差样本被判死也不是因为分数低，是因为 `CRED_ACCESS` 与 `NET_EXFIL` 是 kill 规则。

唯一的脆弱点：如果将来新加的规则打中了**好样本的风险类文本**，好样本会掉到中样本以下。
所以 `tests/` 里留了每次运行的完整输出——规则一改就能看见分数漂移。

## 七、已知误差

- 只认文本模式，看不懂运行时拼接出来的路径。`getattr(__builtins__, "ev"+"al")` 这类绕过一律看不见。
- 中文 description 的长度阈值（40 字）是拍的，英文包会偏严。
- 「不可替代性」用行数近似，写得短但写得准的包会被低估。
- 冲突维度依赖调用方提供的已装清单，清单过期就失效。
